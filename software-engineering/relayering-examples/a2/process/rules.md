# Rules: Message Guard (version A2), a sketch

Two things arrive with A2 and both are rules in the full sense: they say
*when* something must hold and what happens when it does not. The first
group keeps the assurance report between requests, which is the ledger. The
second group says when the claims must hold, which is process control. Both
use the rule template with its *When*, *Decided by*, and *On failure*
fields; the judgment clauses of `process/judgments.md` do not have those
fields, and the difference is the point. Identifiers and wording here are
illustrative; the A2 plan fixes them.

## The ledger

### Ledger-1 · The ledger is the assurance report, kept

| Field | |
|---|---|
| Style | obligation |
| Maintains | the record of every judgment |
| When | at every checkpoint the build plan names |
| Statement | `reports/ledger.md` MUST hold one table per named checkpoint with one row per judgment clause: status, evidence, provenance, and the states of the artifacts the evidence was produced against. A row MUST be generated by `tools/ledger.py` from the evaluations' results and the records, never written from a narrative or a completion note. |
| Decided by | analysis: `tools/ledger.py` regenerates the table and exits non-zero if a row has no evidence behind it |
| Evidence | `reports/ledger.md` |
| On failure | the row is marked *not established* and the checkpoint is not passed |
| Example | the table at checkpoint a2-wave-1 |

### Ledger-2 · Staleness

| Field | |
|---|---|
| Style | staleness |
| Maintains | SQ, CONF, VAL, TR, RQ |
| When | WHEN a file under `specs/` changes; WHEN a file under `guard/` or `tests/` changes; WHEN a stakeholder declares a change of mind |
| Statement | A change under `specs/` makes every SQ, CONF, VAL, and TR row stale. A change under `guard/` or `tests/` makes every RQ and CONF row stale. A declared change of mind makes every VAL row stale, with no file changed. A stale row is kept and marked, never deleted, and is re-established only by running its evaluation again or by a new record. |
| Decided by | analysis: `tools/ledger.py` compares the artifact states each row names with the current tree; a declaration is entered by hand |
| Evidence | the stale marks in `reports/ledger.md` |
| On failure | a row whose evidence is older than the artifact it is about is never shown as established |
| Example | the A1 elicitation changed `specs/conops.md`; the ledger at a1-specs shows VAL stale until the new sign-off |

### Ledger-3 · Dependence

| Field | |
|---|---|
| Style | obligation |
| Maintains | the soundness of Ledger-2 |
| When | at every checkpoint |
| Statement | Every row MUST name the artifact states its evidence was produced against, and the generator MUST derive which rows a change touches from the trace matrix, so that a change to one requirement marks the rows of the clauses linked to it and leaves the others standing. |
| Decided by | analysis: `tools/ledger.py` reads `reports/trace-matrix.md` |
| Evidence | the provenance and dependence columns of `reports/ledger.md` |
| On failure | the generator marks every row of the affected judgment stale, the safe default |
| Example | a change to REQ-2 marks the rows of REQ-2, US-2, SC-3, and SC-4 stale and leaves REQ-1's standing |

## Process control

### WF-1 · The gate stands before every commit

| Field | |
|---|---|
| Style | gate |
| Maintains | RQ, the mechanical part of CONF, and TR |
| When | WHEN work would be committed |
| Statement | Code-RQ-1, Reqs-CONF-1, Scen-CONF-1, Specs-TR-1, and Specs-TR-2 MUST hold for the tree being committed, decided by the exit code of `tools/gate.sh`. |
| Decided by | analysis: the exit code; enforced by the pre-commit hook in `.githooks/`, which runs the same script. Where the hook is not installed the rule is prescribed, not enforced, and the dev log says which. |
| Evidence | the gate header copied into the dev-log entry; the hook's refusal, when it refuses |
| On failure | the commit is not made; the work returns to its task |
| Example | the hook refusing the commit of a test with no marker |

### WF-2 · A specification change is audited before it is relied on

| Field | |
|---|---|
| Style | gate |
| Maintains | SQ |
| When | WHEN a commit would change a file under `specs/` |
| Statement | The latest audit record MUST name the specifications' state being committed with no open gap. |
| Decided by | analysis: `tools/ledger.py` compares the audit record's state line with the tree; the audit itself is Specs-Audit, started by the developer |
| Evidence | `records/audit-NN.md`; the SQ rows of the ledger |
| On failure | the commit is not made until the audit has been run and ruled |
| Example | the A1 commit a1-specs, audited by audit 03 before it was made |

### WF-3 · Wave acceptance is a recorded decision

| Field | |
|---|---|
| Style | gate (approval) |
| Maintains | all five judgments for the wave's scope |
| When | WHEN a wave of the build plan would be accepted |
| Statement | Every row of the ledger for the clauses in the wave's scope MUST be established, including the SQ and VAL rows by their records, and a person MUST record the acceptance with their name, the date, and the checkpoint. |
| Decided by | review (human): the recorded acceptance; `tools/ledger.py` reports whether the rows are established |
| Evidence | the acceptance line in `records/dev-log.md`; the ledger table at the checkpoint |
| On failure | the wave stays open |
| Example | wave 1 of A2 accepted after the architecture clauses' review record was written |

Intermediate commits inside a wave may leave rows not established; the
ledger says so. The gate of WF-1 is about the mechanical rows only, which is
why the two rules are separate.

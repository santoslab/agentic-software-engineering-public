## Goal

The goals of this project are to:
 - get familiar interacting with an agent to design, develop, and maintain a coherent set of artifacts (in this case, files constituting a personal knowledge base),
 - learn the general feel of using an agent to help you turn an initial "sketch" of a project concept into an engineered and maintained specification that guides the development of a system.
 - understand how you can use an agent to "elicit" details from you (interview you, "grill" you) to resolve ambiguities in specifications or to systematically move from sketch to a specification.

Note that engineering a large system will often required tiered specifications (multiple specifications that each introduce more precise details about the system) or specifications that provide different "views" of the same system (where the views are in some what consistent with each other).

You will learn the above ideas by building a maintaining  a **personal knowledge base (PKB) on agentic software engineering**, organized around *your* interests — subfields you want to go deep on (verification, multi-agent systems, prompt design, tooling, economics of agents, safety…).  The PKB should be a resource for you as you are carrying out work in the course.   By the end of the course, it should be the artifact you'd actually want to take with you, holding the key concepts that you learned in the course.  You might actually want to develop other PKBs (or a single larger PKB) for other courses, research areas, etc.

In terms of slogans, we will be learning some basic aspects of "spec-driven development".  To avoid overloading you with technical details that aren't related to the abstract concept of spec-driven development, this project doesn't involve much code or "technology stacks" (some optional parts do).  Everything will be illustrated using only markdown files -- the project has a very low barrier to entry. 

Everything from Lecture 04 applies — elicitation before structure, spec before content, and giving the agent tools to check its work.

Important note: There really is no "right" or "wrong" regarding the structure or the contents of your database.  The point here is to get comfortable with using a coding agent, and learn some of the concepts of spec-driven development, and to reflect on the process of carrying out engineering with a coding agent (who itself as expert-level engineering knowledge).   If you don't like what happens with your initial try, you can also have the agent change or update things later on (which itself is a good thing to learn).


## Format: OKF


Your PKB is a bundle conforming to Google's
[Open Knowledge Format (OKF) spec](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md):

- Every concept note is a markdown file with YAML frontmatter; **`type` is required**
  (you choose the type vocabulary); `title`, `description`, `tags`, `timestamp`
  recommended.
- Reserved files: `index.md` (directory listing / progressive disclosure — no
  frontmatter) and `log.md` (chronological change history — no frontmatter).
- Links: bundle-relative (`/concepts/agent-loop.md`) or relative markdown links.
  Broken links are legal — they mark knowledge you haven't written yet.
- Conformance is deliberately light: parseable frontmatter, non-empty `type`, correct
  reserved files. OKF is explicitly designed for knowledge "authored by humans,
  generated by AI agents" — which is exactly what you'll be doing.

A tiny worked example ships in your starter repo (`pkb-example/` — 3 concept notes,
an `index.md`, a `log.md`). Open it in Obsidian first so you know what "done" looks
like.

## Kickoff task (due end of week 3)

1. **Elicit.** Run a elicitation/grill-me-style session with Claude about your PKB *before creating
   any PKB files*: you want this session to uncover the following - what is the PKB for, who is its future reader (you in week 15; you in two years?), what topic areas, how organized and formatted, how is the material curated and maintained, etc. what does a good note contain, what's out of scope.  For this step, in a single prompt, give the agent: a short description of the purpose of the PKB, the URL to the OKF spec with instructions that you want the PKB organized according to the spec, indicate the goal of the session is to produce a file `pkb-spec.md` that will serve as the specification for humans and agents to follow to set up the PKB, maintain the content in it.  Have Claude write appropriate `CLAUDE.md` files so that a future session can understand the purpose of this project. *Remember*: if you don't know how to tell Claude to do this, just tell Claude what you want to happen, i.e., "I'm planning to clear my context.  I want future sessions understand the purpose of the PKB folder in the repo and the state of its development", and ask Claude what to do to make this happen.  Create a session transcript using the `\transcribe` skill and save this session transcript (TODO: somewhere outside the folder where the PKB lives).  Commit these results.

1a. **Elicit - Assessment**: Review the session transcript.  Try to identify in the transcript elements 
   of the agent loop that we discussed in earlier lectures (user inputs to the conversation, agent responses, 
   tool calls and results of tool calls feeding back into the context/conversation).  In your TODO: engineer-log.md file under a heading `Elicit - Assessment` write down at least two examples of each of the types of agent loop elements mentioned above.   Commit the current state of your assessment.

2. **Specifation Review** Review the produced specification `pkb-spec.md`: folder taxonomy; your concept `type`
   vocabulary (with one-line definitions); required/optional frontmatter fields; note
   granularity rules (what deserves its own file); linking conventions; what `log.md`
   records.  If you make any changes to the specification manually, ask Claude to review your changes (it can see what changed as a diff from your previous commit) and to confirm that the specification remains consistent (or indicate what should be fixed). This is a general concept: The agent helps you produce the spec and keep it consistent.  If you want changes to the spec, you can ask the agent to make the changes (it will generally keep it consistent), or you can make some changes manually, and the agent should review, propagate the effects of your changes or otherwise update the spec to make sure that everything is consistent.  Alternatively, an independent agent can also review the spec and suggest changes.  If your spec changed, commit any updates.

3. **Scaffold.** Clear the agent context (the specification should now carry enough information 
   forward to support development).  Confirm that what was set up in the agent memory system (via the CLAUDE.md files above) are sufficient by asking Claude "What is your understanding of the purpose and state of the PKB project in this repo?"  If Claude has any misunderstandings, you can correct it.
   Have Claude build the bundle from your spec: folders, `index.md`,
   `log.md`, and a `CLAUDE.md` for the PKB repo itself telling future sessions how to
   maintain it (your spec, condensed into operating instructions — memory about
   memory).
4. **Seed.** Write ≥5 concept notes drawn from the weeks 1–3 readings and lectures,
   in your own words, each conforming to your spec and linked from `index.md`.
   (Examples: the agent loop; context windows and caching; spec-driven development;
   the five agentic principles; tool calling. But follow *your* interests.)
5. **Stretch (optional, recommended):** have Claude write a conformance checker — a
   small script or a Claude Code skill that validates every note (frontmatter parses,
   `type` non-empty, reserved files well-formed, index covers all notes) — "give the
   agent tools to check itself," applied to knowledge work.
6. **Your Thoughts:** write a 2-3 paragraph summary of your thoughts about this activity.  What went well, 
   what didn't go well?  Did the agent's behavior match your expectations?  Did anything about 
   the activity surprise you?  What does this activity reveal to you about how the process 
   of implementing software might change for you as you embrace agentic software engineering?

## Looking Ahead -- Continuing to Maintain your PKB (weeks 4–15)

- Add or improve notes weekly (~30 min): new concepts from lectures, lessons from your
  own project sessions, papers/posts you read. Anything you find yourself re-explaining
  to Claude belongs in a note.
- Keep `log.md` current — it's your evidence of accretion at checkpoints.
- Expect later units to plug tooling into it: a note-capture skill (~week 5), subagent
  literature sweeps (~week 9), filesystem/Obsidian MCP (~week 12).

## Checkpoints (completion-based)

- **Week 6:** ≥12 notes; `log.md` shows steady accretion; one note captures a lesson
  from Project 1.
- **Week 10:** ≥25 notes; evidence of restructuring (taxonomy survived contact with
  reality, or the spec was revised — both count); tooling in use.
- **Week 15:** final state + half-page retrospective: what your week-3 spec got wrong,
  and what you'd tell a student designing theirs.
